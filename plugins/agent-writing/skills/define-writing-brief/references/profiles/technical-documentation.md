# Technical documentation

Serve a defined reader working with a particular system or concept. Establish product/version scope and prior knowledge when those details affect correctness. Keep terminology, identifiers, examples, and normative requirements consistent with the supplied source. Mark unknown behaviour rather than completing a plausible contract.

Choose a structure according to purpose: learning, achieving a goal, looking up facts, or understanding reasons. A documentation set can contain all four; each page should give its main task a coherent path. Link to existing related material instead of burying a lookup answer in a lesson.

Include prerequisites, compatibility boundaries, or operational consequences only where supported and relevant. Preserve exact code and distinguish observed results from proposed examples. Documentation does not require Markdown or Google's presentation defaults: follow the selected renderer and presentation profiles. Do not add marketing claims or universal sample-length limits.
