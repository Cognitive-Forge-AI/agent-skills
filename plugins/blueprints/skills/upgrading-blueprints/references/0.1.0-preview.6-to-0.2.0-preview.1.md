# Upgrade to Blueprints 0.2.0-preview.1

This catalog upgrades 0.1.0-preview.6 project memory in place. The store already declares modular adoption, so a conforming store only needs new version stamps. Invoke it only for an explicit upgrade request. It requires no archiving or deletion.

## 1. Inventory and baseline

Use bounded discovery to inventory IDs, types, authored versions, statuses, paths, and relationship endpoints before editing. Capture a trusted baseline outside the active store — a Git revision or a temporary copy — for the comparison in step 5.

Read the target [Core](../../blueprints/references/blueprints/core.md), [Markdown binding](../../blueprints/references/blueprints/markdown-based-implementation.md), and [Project Memory](../../blueprints/references/blueprints/extensions/project-memory.md). Load the [legacy definitions](../../blueprints/references/blueprints/compatibility/legacy-execution.md) only if the store selects them. Load [Working Memory](../../blueprints/references/blueprints/extensions/working-memory.md) only if the request explicitly asks to adopt it.

A store on an earlier version needs the preceding catalogs first. Leave unknown source versions and types unchanged, and report the limitation explicitly.

## 2. Update adoption

In `.blueprints/config.json`, set `blueprints` to the target suite. Keep every extension selection and its mode:

```json
{
  "blueprints": "0.2.0-preview.1",
  "extensions": [
    {"id": "project-memory", "mode": "active"},
    {"id": "legacy-execution", "mode": "reference-only"}
  ]
}
```

The target also defines an optional `working-memory` selection, which requires Project Memory active. Add it only when the upgrade request explicitly asks to adopt Working Memory. The upgrade itself never activates it.

## 3. Check active items against the target

The target changes these rules. None of them requires editing an item that conformed to 0.1.0-preview.6:

- Every type declares durability and a lifecycle under [Core §4.1](../../blueprints/references/blueprints/core.md#41-durability-and-lifecycle). Specs, Decisions, Plans, and Evidence are durable and keep their lifecycles, so each of these items still records `status`.
- A durable item cannot store a relationship to a volatile item. A 0.1.0-preview.6 store has no volatile items, so no existing link is affected.
- Decisions gain the initial status `draft` and the status `withdrawn` under [Project Memory §6](../../blueprints/references/blueprints/extensions/project-memory.md#6-decisions). Existing statuses keep their meaning. Do not move a `proposed` Decision back to `draft`.
- An item of an active extension records the selected suite version under [Core §6](../../blueprints/references/blueprints/core.md#6-project-adoption). Module declarations no longer list `itemVersions`, and an item of a reference-only extension keeps the version it was retained with.
- A reference-only module's dependencies stay selected but may use either mode.

Correct an item only where it fails a target rule, and only as far as its meaning and project authority support. Keep paths, IDs, bodies, creation dates, source provenance, approvals, and relationships.

## 4. Stamp active items

After an item's checks pass, set its `blueprints` field to the target suite. You may check a candidate diff or temporary candidate copy before applying a stamp.

Leave reference-only items byte-for-byte unchanged, including their versions. Leave an unresolved item at 0.1.0-preview.6 and report an incomplete upgrade. Never infer success from the stamp alone.

## 5. Verify and report

- Compare active items with the baseline: identities, locations, content, approvals, provenance, and links remain intact except for version stamps and documented required corrections. The same comparison enforces relationship-creation rules.
- Compare reference-only files byte-for-byte. There must be no changes or missing records.
- Check the selected suite, available definitions, recorded item versions, metadata, durability and lifecycle requirements, targets, relationship reasons/directions, required reciprocals, Spec ancestry, and immutable anchors.
- Run the repository's relevant checks. In a framework checkout, `node scripts/check-blueprints.mjs --root <store> --json` provides focused structural checks and reports any active item still recording another version. `--before <baseline-store>` cannot load a 0.1.0-preview.6 baseline and reports it as incomplete, so compare against the baseline with a diff instead. `--no-git` is incomplete when anchors exist. These development scripts are not assumed installed with the skill; use the definitions directly if unavailable.
- Report changed items, unchanged retained records, advisory findings, incomplete checks, and unresolved items. Re-running the completed upgrade must make no changes.
